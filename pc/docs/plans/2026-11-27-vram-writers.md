# VRAM writers: who puts pixels into the array and who reads them out

Step K0 of [the native renderer plan](2026-11-27-native-renderer.md). Generated by `python3 pc/tools/vram_writers.py` (the table below is its
output; `--check` fails when a site's function is not classified in the tool or a classified function lost its sites, so this does not go
stale). Written 2026-11-27 from the code at the commit that adds it; the classification is by reading each function.

## What the table says

- **105 sites in 63 functions** (the lint's `vram_sdk_calls` counts 71 of them: it does not count `vs_main_loadClut`, the CLUT stager, or
  `pc_frame_move`, the copy item). By cadence: **39 once** (a load), **34 on an event** (an effect starting, a screen opening), **27 every
  step while it runs**, 2 per movie frame, 3 definitions.
- **The live palettes (what must stay data at run time)** are the 10 functions marked K4 live palette: model palette pulses
  (`vs_actors_enableModelPalettePulse`, `vs_actors_updatePalettePulse`), actor appearance transitions
  (`vs_actors_updateActorAppearanceTransition`), a frozen platform's look (`vs_field_setPlatformFreezeAppearance`), a gimmick's palette and
  GIM image sets (`vs_field_createGimmickInstance`, `vs_render_updateGimImageSet`), the title menu's item palettes (`_setMenuItemClut`,
  blended by a factor each step), MENUF's two pulses, and `vs_main_loadClutTransition`. Every palette write goes through
  `vs_main_loadClut` (33 call sites) and ends in `vs_main_commitClut`, which is the one place a native palette object can be set from.
  Everything else that writes a CLUT is a load (`parseShp`, `loadMaterialPalette`, `vs_field_uploadRoomPalettes`, `_loadSystemDat`, the
  menus' sheets) and can be baked.
- **Texture animation** is two families: room type 1 (`vs_field_animateRoomTextureImages` and the trigger markers' frames, `MoveImage` of
  atlas frames and scrolls: frame indices) and actors' texture maps (`vs_actors_textureFrameMove`, `textureOverlayMove`,
  `stepTextureScrolling`, `func_800AACDC`, `vs_render_queueTextureRectangleMove`: `pc_frame_move` copy items, per step).
- **Dynamic images** (textures the game composes itself, which a converter cannot produce): `renderImage` and MENU7's `_renderImage`
  (images drawn into VRAM), `renderTextImmediate` and `vs_render_blendGlyphIntoPixels` (glyph pixels read back with `StoreImage`: typed text
  replaces them), and the title's two fades (`_fadeInMenu`, `_fadeInMenuCopyright`: a picture blended in a buffer and uploaded each step,
  which is a typed fade over a sheet).
- **Readers of the frame** (`pc_frame_read`, which fences a capture of the drawn area into the array): 3 sites: TITLE 22C.c lines 4054
  and 4689, MENU5 4D8.c 307. Reads of areas the array holds exactly (`pc_vram_read`: transfer and texture areas): TITLE 106, 4047, 4051,
  MENU5 306, MENU7 260.c 211 and 3563. The renderer's own readers of VRAM at record time are listed by the `vram_pointer` lint (11 sites).
- **Movies** write 2 sites per frame through MDEC into the 24-bit display.
