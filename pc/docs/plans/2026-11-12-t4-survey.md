### 2d. Packet addresses stored as 4 bytes
- Not in game structs: since the LP64 move the scratch pointers are real 8-byte pointers (`scratch.h:13`; `psx_ptr(T)` is `T*` on 64-bit, `psx_types.h:133`).
- OT links are inherently 24-bit words in packet tags (`*head & 0xffffff`). The packet-ordering memory is guest RAM only because link words are 24 bits (`boot_runtime.c:794-806`, `build_boot.py:2292`).
- The text-box OT page pointer `D_800F51B8` and the 3-page ring `D_800EB9CE` (`func_800CB83C.zig:137-138`) are stored in game globals.
- Marker packets store item indices, not addresses (`draw_items.c:~595-603`), so they survive save states.

## 4. Target design and migration

### Target
Per-frame **`pc_frame`** value (plain data, no pointers), built on the game thread and handed whole:
- **Header:** draw env, display env, frame-buffer index, game tick, camera/projection record (the GTE screen record the hw path reads today), widescreen layer base.
- **Buckets** (0x822 slots, plus named sub-lists such as the text-box page): per bucket an ordered list of **commands**, in the order the OT would walk them:
  - `ITEM(index)` (the existing `pc_item`).
  - `NATIVE_LIST(list)` and `NATIVE_TRANS(list, first, count)`.
  - `RAW(words, n)` for not-yet-converted GP0 packets.
  - State entries are already item kinds.
- **Item attributes replace address ranges:** `anchor`, `opacity`, `span`, `hw_hidden` (exists), `covered_by(list)`, `interp_key` (stable id). `pc_hw_*_packets(start,end)` calls become attribute writes on the entries.
- Sort key stays `(bucket desc, insertion asc → draw reversed)`, i.e. the item rule already implemented.
- Consumer: `pc_hw_item(item)` calling the existing `pc_hw_rect/shape_triangle/line` directly (until T5 removes the CPU raster, `lower` + `commands()` stays so VRAM stays exact).

### Bridge that lets converted and unconverted producers share one frame: OT adoption at DrawOTag
At `DrawOTag`/`pc_frame_draw`, one pass over the guest OT chain per slot:
- Copies each packet's words into the frame (a RAW entry, or items via the decoder `pc_frame_add_packets`, draw_items.c:131 and the lift path).
- Translates marker packets (render/translucent/`pc_frame_marker`) into native bucket entries.
- Resolves the address-range registries (native coverage, anchors, opacity, spans, interpolation keys) into per-entry attributes, because each packet's address is known at that moment.
- Then the existing walk body iterates the frame, not guest RAM.

Properties:
- Guest OT and packet RAM is read at exactly one point.
- Every unconverted producer stays unchanged.
- The stream digest is equal by construction (same words, same order).
- The frame becomes a self-contained value even before the last producer converts. This is the step that lets T1 and T2 work start in parallel with the producer conversion.
- It reverses the transition's direction: markers become an input format to adoption, then disappear as producers write bucket entries directly.

## 5. What it unblocks

- **Pinned imports (12 today):** D_800F4CD0 (S2/S6), D_800E856C/8594/85BC (S4), D_800F1A68/1A78 (the sprite/wipe state around `func_8007D360..D734`, S3, unverified), D_800E9C00/08/0C (used in 4A0A8.c: `script_special_op`, `func_800BBBE8`, unverified), vs_battle_mapCompletionFlags (touches packet storage by adjacency). `vs_main_drawEnv/dispEnv` leave guest RAM when the draw/display env become frame-header values. They are listed with T6 as well.
- **T15 counts:** `gpu_packet_writes` 75 to 0, `lift_bridge` 13 to 0, `zig_raw_memory` about 90 lower (packet builders listed in 2b; total now 983), `ps1_address` 7 to 6 (`func_800C64D0`), part of `address_as_integer` (OT address arithmetic; count not measured). The scratchpad count (52) is mostly hardware registers and is not affected.
- **T1, what is still needed after T4:**
  - VRAM: textures and palettes are written by the game thread (`LoadImage`/`MoveImage`/palette writes), and the walk reads VRAM and the GPU target (stale-area readbacks `pc_hw_sync`). A renderer thread needs either T5 or a versioned VRAM-update stream queued with the frame.
  - Game-side hooks that run inside the walk and call into the renderer on the game thread (classic layer, hud bridge, `ui_text` reports, `pc_hw_anchor_packet`) must become frame-build-time attributes.
  - Shared projection state (`pc_scene_camera_get`, `vs_gte_screen` record) must be in the frame header (T7 partly done by the record).
  - Triple-buffer the frame (the item list is a single static array in saved state).
  - RPC, editor and HUD reads of game structs off-thread (T13/T17).
- **T2, after T1+T4:** the present loop takes (previous, current) frames, real-time phase, and can re-rasterise 2D items at display resolution each present. 2D smoothness (menus, HUD) needs item identity keys (today packet addresses, `gpu_hw.c:4854`).

### "Present at display rate while the game steps at its fixed rate": possible now, in a limited form
- Infrastructure exists: `pc_window_present_rate` (`boot_window.c:757`, "match display", capped by the display rate), extra presents at fractions (`boot_runtime.c:1336-1346`), native-list interpolation by `pc_present_phase`, the present passes separate from drawing (the target is drawn during DrawOTag; present re-lights and composes it).
- What it needs, none of which depends on T4 completing:
  1. Phase from real elapsed time since the frame arrived, not `k/n` of a field (`pc_window_wait_fraction`, `pc_window_tick`).
  2. A display-vblank-paced swap instead of sleeping to 59.94 Hz deadlines.
  3. Frame duration = the game's tickspeed times the field.
- Limits before T1/T4: presents happen only while the game is inside `VSync`, so game work (logic plus DrawOTag) cannot overlap a present and a slow game frame still repeats a picture. Everything drawn as 2D (HUD, menus, text, packet effects) stays in the baked target and steps at game rate. The VRAM readback and replay checks (`op_rewritten`) tie replays to the exact VRAM state. This is the "display-rate pacing as a patch" the plan parks, so treat it as an experiment, not the T2 solution.

## 6. Risks and decisions for the owner
1. **Retire native-off modes and the software presenter** (S5). Without that, 3D packets cannot stop being built. The OpenGL path is contributors' to maintain (memory: retired-32bit).
2. Adoption (S1) copies packet words per frame (up to 128 KB; negligible), but must keep `drawing_tag`-style adjacency exact for popup digits and bubbles.
